# Decisions

A log of decisions that shape the shipped app (its scope, formats, and model behavior), newest first. A decision that becomes a rule (in `CLAUDE.md` or `.claude/rules/`) isn't logged here, since the rule records it. Undecided questions live in [outstanding-questions.md](outstanding-questions.md) until they're settled. Add a row when a decision is made, deferred, or reversed; a reversal gets its own row rather than an edit to the old one.

| Date | Decision | Why | Where it applies |
| --- | --- | --- | --- |
| 2026-11-28 | **Each manifest format's kit owns everything about that format, validation included. The schema layer owns only converting the kit's models into `PayloadSchema`.** This narrows the row below, which gave the schema layer the job of interpreting each format. `ProfileManifestKit` will check a manifest's conformance to the ProfileManifests spec, meaning the rules the spec states (a default must match `pfm_type`, `rangeListTitles` must match `rangeList` in count, `valueInverted` is only valid on booleans) and report each problem. The planned `SchemaDiagnostic` cases that check spec rules move to the kit. Cases about app policy, such as unparsable versions and conditions the app doesn't model, stay in the schema layer. | Adding a format, such as Apple's YAML manifests, shouldn't make the app learn that format's rules. With validation beside decoding, each format's rules are implemented and tested in one place, and each converter only maps that format into the app's model. | `ProfileManifestKit`; `ProfilePal/Schema/` and its converters; the `SchemaDiagnostic` cases |
| 2026-11-28 | **Manifests reach the app in two steps: source plist → `ProfileManifestKit` models → the app's format-neutral schema layer (`PayloadSchema`).** The app doesn't convert manifest plists straight into its own model. | `ProfileManifestKit` owns implementing the ProfileManifests spec, extensions included, as faithfully as possible. The schema layer gives the app one consistent model whatever the source format, and owns cleaning up and interpreting each format into something easier to work with. Converting straight to the app's model would take fewer steps and possibly less code, but it would bury the spec implementation inside the conversion and make conformance to the spec hard to unit test. | `ProfileManifestKit`; `ProfilePal/Schema/` and its converters |
| 2026-11-22 | **CodeQL code scanning is removed; re-adding it is deferred until CodeQL supports Swift 6.4 and Xcode 27.** Default setup is off and no CodeQL workflow is checked in. | The project needs Xcode 27, and CodeQL [can't trace builds on Xcode 27 or analyze Swift 6.4](https://github.blog/changelog/2026-10-19-codeql-changes-for-macos-27-xcode-27-and-swift-6-4/), so the Swift scan crashed under default setup and hung under advanced setup. Rather than keep a scan of the workflows alone, CodeQL is removed entirely. | CI (`.github/workflows/`) |
| 2026-11-21 | **`Version` keeps both `original` and `description`, though `description` returns `original`.** | `original` says what the value means (the exact string the version was parsed from), while `description` is the `CustomStringConvertible` hook for interpolation and printing. Keeping both names reads better at call sites than storing the string only as `description`. | `VersionKit.Version` |
| 2026-11-21 | **Versions are parsed by a `VersionKit` framework that accepts any number of dot-separated numeric parts.** Leading zeros parse as integers, missing trailing parts count as zero, and the original string is kept for display. Pre-release and build suffixes and a leading `v` aren't accepted. ProfileManifestKit keeps versions as strings; the app's schema layer parses them. | Of the 5,479 version values in ProfileManifests' 288 manifests at `0d01e64`, 99.5% are 1 to 4 numeric parts (4-part ones such as Cloudflare WARP's `2024.1.160.0`, and leading zeros such as OneDrive's `20.033`). None use semver suffixes or `v`. The rest are 14 empty strings and 29 wildcards or notes such as `15.x` and `16.27 ONLY`. Strict semver packages reject 1- and 2-part versions, and the spec types versions as strings. | `VersionKit.Version`; the schema converter's availability parsing |
| 2026-11-21 | **`ManifestTargetCondition` models `pfm_platforms`.** A condition with no `pfm_target` that tests only the platform now decodes with `platforms` set. `pfm_n_platforms` and `pfm_distribution` stay unmodeled. | The spec's conditions example documents `pfm_platforms` in a condition, and 3 conditions in Apple's CalDAV, CardDAV, and Extensible SSO manifests use it. The app's schema layer needs it to evaluate those conditions. The other two keys aren't documented for conditions (see [outstanding-questions.md](outstanding-questions.md)). | `ManifestTargetCondition.platforms` |
| 2026-11-20 | **Sharing the properties `Manifest` and `ManifestField` both declare is deferred.** Both still declare `note`, `supervised`, `userApproved`, `platforms`, and the iOS, macOS, and tvOS min, deprecated, and max versions, each with its own doc comment and `CodingKeys` case. | Deferred on purpose for now. A shared type would need its own decoding and doesn't fit the flat property-order rule. | `Manifest`, `ManifestField` |
| 2026-11-20 | **The manifest model structs are `Decodable` only, not `Codable`.** `Manifest`, `ManifestField`, `ManifestTargetCondition`, `ManifestConditionalRule`, and `ManifestExclusionRule` can't be encoded; `PlistValue` and the enums stay `Codable`. | The app reads manifests and writes profiles, a different format. Synthesized encoding never called `coerced(to:)`, so re-encoding a manifest silently wrote whole-number `<real>` values as `<integer>`. | The manifest model structs |
| 2026-11-20 | **v1 prioritizes loading existing manifests, even malformed ones; v2 or later will handle malformed manifests gracefully and implement the spec more strictly.** In v1, spec-required keys that real manifests leave out are optional, and spec quirks real manifests rely on are accepted. | v1 should be useful immediately with the manifests that exist today. | The model decoders; the optional-keys rule in `CLAUDE.md` |
| 2026-11-20 | **`Manifest.interaction` and `Manifest.lastModified` stay optional, though the spec requires `pfm_interaction` and `pfm_last_modified` on a payload.** | v1 prioritizes loading existing manifests. | `Manifest.interaction`, `Manifest.lastModified` |
| 2026-11-20 | **Unmodeled documented keys are deferred; whether to v1 or v2+ isn't decided.** v2+ should support every key in the base and extended spec. ProfileCreator- and iMazing-specific keys are decided case by case. Still unmodeled: `pfm_allowed_file_types`, `pfm_default_copy`, `pfm_value_copy`, `pfm_description_extended`, `pfm_description_reference`, `pfm_enabled`, `pfm_excluded`, `pfm_hidden`, `pfm_value_decimal_places`, `pfm_substitution_variables`, `pfmx_comment`, the 10 ProfileCreator-only keys, and, on conditions, `pfm_value_empty` and `pfm_domain`. They're dropped when present. | Not needed for v1's first UI; supporting the full spec belongs with v2's stricter spec work. | `Manifest`, `ManifestField`, `ManifestTargetCondition` |
| 2026-11-20 | **A conditional's `require` accepts `.alwaysNested`.** Field and conditional rules share `ManifestRequirement`, though the spec lists only `always` and `push` for conditionals. | v1 prioritizes loading existing manifests; `com.jamf.connect.login-OpenID` uses it in a conditional. A separate two-case enum would enforce the spec but reject that manifest. | `ManifestConditionalRule.require` |
| 2026-11-20 | **Real-manifest test fixtures come only from projects that publish their manifests under an open-source license.** The smoke tests use unmodified manifests from xCreds (BSD-3-Clause) and macOSLAPS (MIT); ProfileManifests' manifests aren't committed. | ProfileManifests has no license (the MIT text in its `ACKNOWLEDGEMENTS.md` covers Apple's schema), so redistributing its files isn't clearly allowed. Neither open-source manifest uses conditions, so conditions are covered by synthetic fixtures only. | `ProfileManifestKitTests/Fixtures/Manifest/`, its `THIRD-PARTY-NOTICES.md`, and `ManifestTests.loadRealWorld` |
| 2026-11-20 | **Manifests should eventually load even when partly malformed, with each problem flagged in the GUI.** Deferred: for now, one invalid value fails the whole manifest, as `ManifestFieldTests.unknownType` and `ManifestTests.unknownInteraction` pin. When it's built, those tests should expect a finding instead of a thrown error. | Real manifests often break the spec in small ways (12 of ProfileManifests' 288 failed before the recent model fixes), and rejecting a whole manifest for one bad value hides everything that's valid. | Manifest loading (`Manifest.load(from:)` and the model decoders); the GUI |
| 2026-11-20 | **`ManifestTargetCondition.target` is optional, though the spec requires `pfm_target`.** A condition without it still loads, with `target` set to `nil`. | The spec's own conditions example omits it, and 4 of ProfileManifests' 288 manifests have conditions that test the platform or install method instead of a field. They load only if it's optional. | `ManifestTargetCondition.target` |
| 2026-11-20 | **`Manifest.unique` is optional, though the spec requires `pfm_unique` on a payload.** A manifest without it still loads, with `unique` set to `nil`. | 3 of ProfileManifests' 288 manifests leave it out, and they load only if it's optional. | `Manifest.unique` |
| 2026-11-16 | **Nested values are coerced against the field's schema.** `PlistValue.coerced(to: ManifestField)` recurses into arrays (via the first subkey) and dictionaries (via the subkey with the same name). Keeping `<real>` and `<integer>` apart at decode time is deferred unless coercion keeps causing bugs. | The field type alone can't say what an array's items are; the subkeys can. | `PlistValue.coerced(to:)` |
| 2026-11-02 | **Manifests are XML plists only in v1.** Binary manifest support, and binary-format manifest tests, are deferred to v2. | Keeps v1 scope to the format ProfileManifests ships. | Manifest loading and its tests. When binary support is added, run the `PlistValue` fixture decode tests and the `load(from:)` test against binary plists too, converting the XML fixtures in the test with `PropertyListSerialization` rather than committing binary copies. |
